## 1. 背景

架空の会社「サンプル商事」（社員約80名・5部署）では、貸出用のノートPC・モニター・プロジェクターなどを総務部が Excel の台帳で管理している。貸出の申請は口頭とメール、返却の確認は総務部の担当者が台帳を見て個別に声をかけている。社内は Microsoft 365（Business Standard）を使っている。

## 2. これまでの課題

| 課題 | 内容 |
|------|------|
| 在庫が分からない | 今どの備品が空いているかを、総務部に聞かないと分からない。台帳の更新漏れで、貸出中の備品を二重に貸すことがある。 |
| 承認の記録がない | 上長の了承が口頭やメールで、誰がいつ認めたかが残らない。 |
| 返却の遅れ | 返却期限を過ぎても気付かず、次の利用者が困る。担当者が毎回声をかけている。 |
| 故障の連絡が埋もれる | 故障の連絡がメールやチャットに散らばり、修理の対応状況が分からない。 |
| 集計が手作業 | 毎月の貸出件数・延滞件数を、担当者が台帳から手で数えている。 |

## 3. 目的

- 社員が自分で空いている備品を探し、貸出を申請できるようにする。
- 上長の承認を記録に残し、承認された時点で台帳を自動で更新する（二重貸しをなくす）。
- 返却期限の前日に知らせ、期限を過ぎたら自動で督促する。
- 故障の報告を一か所で受け付け、修理の対応をタスクとして管理する。
- 毎月の集計を自動で作る。
- 追加の有料ライセンスを使わず、Microsoft 365 Business Standard の範囲で作る。

## 4. 要件一覧

| ID | 要件 | 種別 |
|----|------|------|
| REQ-001 | 社員は、備品の一覧を区分・状態で絞り込んで見られる | 機能 |
| REQ-002 | 社員は、備品を選び、利用目的・期間（先の日付の予約を含む）を入れて貸出を申請できる | 機能 |
| REQ-003 | 修理中・廃棄の備品、上限日数を超える期間、予約受付日数より先の開始日、承認待ち・予約済み・貸出中の記録と重なる期間の申請は受け付けない。同時に申請された場合も二重に受け付けない | 機能 |
| REQ-004 | 申請は承認者に承認依頼として届き、承認・却下とコメントが記録に残る。承認期限を過ぎたら期限切れにする | 機能 |
| REQ-005 | 承認されたら、貸出記録を自動で予約済み（開始日が先）または貸出中にし、申請者にメールで知らせる | 機能 |
| REQ-006 | 申請・承認・却下・督促の上限到達を、Teams のチャンネルに知らせる | 機能 |
| REQ-007 | 社員は、自分の貸出の一覧から返却を登録でき、開始前の申請・予約を取り消せる | 機能 |
| REQ-008 | 返却期限の前日に申請者へ知らせ、期限を過ぎたら毎日督促する。督促が上限に達したら管理者に知らせる | 機能 |
| REQ-009 | 故障・不具合は Forms で報告でき、Planner に対応タスクを作り、備品の状態を「修理中」にする。タスクが完了したら「利用可」に戻す | 機能 |
| REQ-010 | 毎月1日に、前月の貸出件数・延滞件数・故障件数を集計し、CSV を SharePoint に保存して管理者に知らせる | 機能 |
| REQ-011 | 承認者・管理者・上限日数・督促の上限などの設定は、SharePoint の設定リストで変えられる（フローを直さない） | 運用 |
| REQ-101 | 追加の有料ライセンス（プレミアムコネクタ・Dataverse の容量の追加購入）を使わない | 制約 |
| REQ-102 | フロー・アプリはソリューションにまとめ、書き出したファイルから別の環境に再現できる | 保守 |
| REQ-103 | 処理に失敗したら、管理者に知らせ、どの申請で何が失敗したかを記録に残す | 非機能 |
| REQ-104 | 社員はリストを直接変更できず、申請・返却・取消はアプリ経由の確認を必ず通る。本人の記録しか操作できない。備品台帳・設定は管理者だけが変更できる | セキュリティ |

## 5. 対象外

- 備品の購入・資産計上（会計システムとの連携）
- バーコード・QR による貸出・返却の読み取り
- 複数拠点の在庫の移動

## 6. 前提と制約

- デモの環境には社内のユーザーが1人しかいないため、申請者と承認者・管理者は同じアカウントで動かす。本番では設定リストの承認者・管理者を別の人にする。
- データはすべて架空のサンプル。
